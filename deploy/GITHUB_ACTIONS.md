# Автодеплой фронтенда

Workflow: [frontend.yml](../.github/workflows/frontend.yml).
Серверный скрипт: [deploy_frontend.py](deploy_frontend.py).

## Порядок работы

1. Pull request в `main` проверяет серверный скрипт и собирает фронтенд.
2. Push в `main` после успешной сборки автоматически публикует её на ВМ.
3. Ручной запуск **Run workflow** деплоит только при выборе ветки `main`.

Сборка выполняется на GitHub: Node.js 24, `npm ci`, `npm run build`.
React-проект публикуется в корне сайта, поэтому `PUBLIC_URL=/`.
Ошибки компиляции останавливают job; существующие предупреждения ESLint
выводятся в журнал без остановки сборки (`CI=false` только для этого шага).
Этот workflow проверяет сборку, а не пользовательские сценарии в браузере.

Для деплоя сохраняется архив готового `build` с SHA коммита. Он хранится
в GitHub Artifacts один день. По SSH на ВМ передаётся именно эта сборка;
Node.js и npm на ВМ не запускаются.

## Как устроена публикация на ВМ

Используется существующий стек `/root/net-genius`:

- Git checkout фронтенда: `/root/net-genius/frontend`, ветка `main`.
- Опубликованные файлы: `/root/net-genius/frontend/build`.
- Корневой nginx уже подключает этот каталог в `/usr/share/nginx/html`.
- Compose project: `net-genius`.

Скрипт проверяет отсутствие локальных изменений, получает `origin/main`
и сверяет полный SHA. Устаревший запуск пропускается, разошедшаяся локальная
ветка приводит к ошибке. `reset`, `clean` и автоматическое удаление локальных
правок не используются.

Архив распаковывается во временный закрытый каталог. Проверяются типы и пути
файлов, размер, SHA сборки и наличие всех файлов из `asset-manifest.json`.
Символьные ссылки, выход за пределы каталога, `.git` и `.env` запрещены.
Лимиты: 256 МиБ для архива, 512 МиБ после распаковки, 20 000 записей.

Перед публикацией проверяется, что запущенный nginx монтирует именно
существующий каталог `frontend/build`. Сам каталог не заменяется: иначе
Docker bind mount мог бы продолжить показывать старую директорию.
Сначала публикуются ресурсы, затем manifest и `index.html`, последним —
`deploy-version.txt`. Каждый файл заменяется атомарно. Старые ресурсы
сохраняются для уже открытых вкладок; автоматической очистки Docker нет.

После публикации скрипт проверяет публичный HTTPS: маркер должен содержать
ожидаемый SHA, а HTML — совпадать с собранным файлом. Несовпадение означает
ошибку job. Полного автоматического отката и резервных копий нет.

Используется общая с бэкендом блокировка `/run/lock/simulteh-deploy.lock`:
публикация фронта не выполняется одновременно с деплоем бэкенда.
Compose, nginx-конфиг, сертификаты, контейнеры фронта, бэка и БД при этой
публикации не изменяются и не пересоздаются. Nginx видит новые файлы
через уже существующий bind mount.

## Однократное подключение

Перед первым запуском нужно сохранить актуальные исходники с ВМ в GitHub.
Неопубликованные изменения в рабочем каталоге блокируют деплой. Если на ВМ
были новые версии игры, стили, страницы или исправления API, они должны
попасть в `main` до его первой автоматической публикации.

Изменения на ВМ выполняются после отдельного подтверждения пользователя.
Обычные последующие push в `main` обновляют сайт автоматически; отдельное
подтверждение для каждого запуска не требуется после подключения.

### Скрипт и ключ на ВМ

Проверенную копию `deploy_frontend.py` установите как отдельный root-owned
файл `/usr/local/sbin/simulteh-frontend-deploy`, права `0755`.
Это не ссылка на файл из репозитория. Изменения самого серверного скрипта
устанавливаются отдельно; обычные изменения сайта этого не требуют.

Для Actions используйте отдельный Ed25519-ключ без passphrase.
Существующие ключи не заменяются. Строка нового ключа в
`/root/.ssh/authorized_keys`:

```text
restrict,command="/usr/local/sbin/simulteh-frontend-deploy" ssh-ed25519 <PUBLIC_KEY> github-actions simulteh/frontend
```

Каталог `.ssh` должен иметь права `0700`, `authorized_keys` — `0600`.
Этому ключу разрешена только команда `deploy <40-символьный SHA>`.
Архив передаётся на stdin. Произвольная shell-команда, PTY и forwarding
для ключа Actions не разрешаются. Приватный ключ бэкенда не переиспользуется.

### Секреты репозитория `simulteh/frontend`

**Settings → Secrets and variables → Actions → Repository secrets**:

| Secret | Содержимое |
|---|---|
| `DEPLOY_SSH_KEY` | Полный приватный ключ фронтового деплоя с переводами строк |
| `DEPLOY_KNOWN_HOSTS` | Проверенная SSH host-key запись существующей ВМ |

Используйте уже проверенную запись сервера, а не непроверенный `ssh-keyscan`.
Пример чтения существующей записи: `ssh-keygen -F 212.67.12.82`.
Строки комментариев с `#` в secret не нужны. Проверка host key включена.

Необязательные **Repository variables**:

| Variable | По умолчанию |
|---|---|
| `DEPLOY_HOST` | `212.67.12.82` |
| `DEPLOY_USER` | `root` |
| `DEPLOY_PORT` | `22` |

Для нестандартного порта known-hosts запись должна соответствовать
`[host]:port`. Пароль root, SMTP, JWT и пароль администратора приложения
для этого workflow не нужны. Переменные React, попавшие в собранный JS,
публичны; серверные секреты не передаются в сборку фронтенда.

## Проверка и повторный запуск

Ожидаются успешные jobs **Build** и **Deploy to VM** для `main`.
В PR **Deploy to VM** должен быть **Skipped**.

Проверки после деплоя:

```bash
curl --fail --silent --show-error https://www.simultech.ru/deploy-version.txt
curl --fail --silent --show-error https://www.simultech.ru/api/auth/ping
```

Первая команда возвращает SHA опубликованного фронта, вторая — `pong`.
Если старая вкладка показывает прежний интерфейс, обновите страницу с
перезагрузкой кэша. Обработчики входа и кабинетов должны использовать
актуальные API; сам деплой не переписывает адреса в исходниках приложения.

Проверки скрипта без ВМ, npm и Docker:

```bash
python3 -B -m unittest discover -s deploy/tests -p 'test_*.py' -v
```

Если job сообщает о локальных изменениях или расходящейся ветке, сначала
разберите их вручную. Ошибка архива, диска или nginx mount останавливает
публикацию. После ошибки проверки HTTPS сайт уже мог получить новые файлы:
проверьте причину и повторите workflow для текущего `main`.

Официальные справки: [setup-node](https://github.com/actions/setup-node),
[upload-artifact](https://github.com/actions/upload-artifact),
[download-artifact](https://github.com/actions/download-artifact).
